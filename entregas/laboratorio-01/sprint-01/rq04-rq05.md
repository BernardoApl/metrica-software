## RQ04 — Sistemas populares são atualizados com frequência?

**Métrica:** tempo até a última atualização.

| Item | Definição |
|---|---|
| Campo utilizado | `pushedAt` |
| Data de referência | Instante da coleta, em UTC, capturado uma única vez e aplicado a todos os repositórios |
| Fórmula | `(data_referência − pushedAt) / 86400` |
| Unidade | Dias (número real, 2 casas decimais); também exposto em horas |
| Ausentes | `pushedAt` nulo → métrica `None` + status `sem_push`; repositório mantido no dataset, fora das agregações |

### Por que `pushedAt`

O enunciado não diz qual campo da API representa "a última atualização", e há
três candidatos com semânticas diferentes:

| Campo | O que realmente marca |
|---|---|
| `updatedAt` | Qualquer alteração no registro do repositório, **inclusive metadados** (descrição, topics, settings) |
| `pushedAt` | Último push de código, em qualquer branch |
| `defaultBranchRef.target.committedDate` | Data do último commit no branch padrão |

`updatedAt` é inflado por eventos que não são desenvolvimento — editar a
descrição já o atualiza —, o que faria repositórios inativos parecerem ativos.
`committedDate` do branch padrão ignora atividade em branches de trabalho e é
nulo quando não há branch padrão. `pushedAt` captura atividade de código sem
depender de um único branch.

Os outros dois campos **são coletados mesmo assim**, como comparativos
auditáveis (`rq04_comparativo_updated_at` e
`rq04_comparativo_ultimo_commit_branch_padrao`), para que a escolha possa ser
justificada com dados no relatório final. Eles não entram no cálculo. O
`validar_amostra.py` reporta em quantos repositórios `updatedAt` e `pushedAt`
diferem em mais de um dia — é a evidência empírica de que os campos não são
intercambiáveis.

### Outros status possíveis

- `data_invalida` — timestamp não interpretável (defesa contra resposta malformada).
- `data_futura` — `pushedAt` posterior à referência (defasagem de relógio); o valor é limitado a `0.0`.

## RQ05 — Sistemas populares são escritos nas linguagens mais populares?

**Métrica:** linguagem primária de cada repositório.

| Item | Definição |
|---|---|
| Campo utilizado | `primaryLanguage.name` |
| Preservação | Nome guardado **exatamente** como a API devolve (`C++`, `C#`, `Jupyter Notebook`), sem normalização |
| Ausentes | `primaryLanguage` nulo → `rq05_linguagem_primaria = None` e categoria `"Sem linguagem definida"`; **nunca descartado** |
| Comparação com o ranking | Ignora maiúsculas/minúsculas, mas o valor armazenado é sempre o da API |

O nome não é normalizado porque é a chave de agrupamento da **RQ07** ("divida os
resultados das RQs 02, 03 e 04 por linguagem") — qualquer normalização aqui se
propagaria para a análise dos outros integrantes.

Repositórios sem linguagem não são descartados porque entre os mais estrelados
do GitHub há uma parcela relevante de repositórios de conteúdo (listas
*awesome*, coleções de livros, roadmaps). Removê-los distorceria a distribuição
da RQ05.

### Fonte de "linguagens mais populares"

Exigida explicitamente pelo enunciado e **fixada aqui para todo o laboratório**:

> **GitHub Octoverse 2025** — "Octoverse: A new developer joins GitHub every second as AI leads TypeScript to #1", publicado em 28/10/2025.
> <https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/>

**Justificativa:** a população analisada é composta por repositórios do GitHub,
então rankear popularidade pelo relatório do próprio GitHub mantém a mesma
população e o mesmo construto (uso real por desenvolvedores). O TIOBE mede
presença em buscadores, vagas e cursos — construto diferente.

## Como integrar com os outros integrantes

O acoplamento é mínimo, por dois pontos:

**1. Fragmento de campos.** `consulta.py` expõe `CAMPOS_RQ04_RQ05`. O script
único do grupo monta a query concatenando os fragmentos de cada um — ninguém
reescreve a query do outro. Campos repetidos entre fragmentos não são problema:
o GraphQL funde seleções idênticas do mesmo campo.

```python
montar_consulta((CAMPOS_IDENTIFICACAO, CAMPOS_RQ04_RQ05, CAMPOS_RQ01_RQ02, CAMPOS_RQ03_RQ06))
```

**2. Função de cálculo.** Cada módulo expõe `calcular(no, referencia)`, que
recebe o nó `Repository` cru e devolve um dicionário de chaves prefixadas
(`rq04_*`, `rq05_*`). A fusão é uma atualização de dicionário, sem colisão de
chaves — há um teste que garante isso (`test_chaves_das_duas_rqs_sao_disjuntas`).

```python
registro.update(rq04_atualizacao.calcular(no, referencia_data))
registro.update(rq05_linguagem.calcular(no, referencia_linguagens))
```

## Como executar

Token do GitHub (escopo `public_repo` basta) via variável de ambiente, `.env` na
raiz (veja `.env.exemplo`, já no `.gitignore`) ou `--token`.

```bash
$env:GITHUB_TOKEN = "ghp_xxx"
```

Testes offline (não precisam de token nem de rede):

```bash
python -m unittest discover -s codigo-fonte/testes -v
```

Validação individual na amostra de 5–10 repositórios:

```bash
python codigo-fonte/testes/validar_amostra.py --quantidade 8
```

Coleta completa dos 100 repositórios:

```bash
python codigo-fonte/coleta/executar_coleta.py
```

## O que a validação de amostra verifica

Conforme o enunciado ("validação rápida numa amostra de 5-10 repositórios"),
`validar_amostra.py` bate contra a API real e checa quatro grupos:

1. **Repositórios esperados** — quantidade, formato `dono/nome`, ausência de
   duplicatas, ordenação decrescente por estrelas, total disponível maior que a
   amostra.
2. **RQ04 correta** — recálculo independente dos dias a partir do `pushedAt`
   cru, comparado com o valor do módulo; data de referência única e em UTC;
   campo declarado é `pushedAt`; nenhum valor negativo.
3. **RQ05 correta** — linguagem idêntica ao `primaryLanguage.name`, caractere a
   caractere; nenhuma normalização; rank existe se e somente se a linguagem
   está no ranking.
4. **Ausentes tratados** — categoria própria para repositórios sem linguagem,
   métrica nula (e não zero) para repositórios sem push, e a soma das contagens
   batendo com o total (ninguém sumiu no caminho).

Os casos de ausência que podem não aparecer numa amostra pequena estão cobertos
de forma determinística em `test_rq04_rq05.py`, com fixtures e data de
referência fixa.
